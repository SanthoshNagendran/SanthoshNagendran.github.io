EV charging infrastructure · embedded → cloud → operator

The site loses internet.
The chargers keep charging.

Most connected EV chargers are only as good as their uplink. Cut the internet and charging stops, sessions vanish, and nobody gets billed. I built an offline-first control plane where the outage is just another state — the cars keep charging, every session is recorded, and the moment the link returns it is all replayed into the billing system, backdated, with no double-charging.

Section 01 · the signal path

One command, all the way down

These are numbered because they genuinely are a sequence: an operator tap in a browser has to cross every one of these layers, in order, to move a relay inside a charger. I worked on all of them.

Layer 1 · silicon

Power board & the car

STM32 / AVR · J1772 Control Pilot · contactor · fault sensing

The only part touching mains and the vehicle. It sets the Control Pilot duty that tells the car how many amps it may draw, closes the relay, and detects ground faults, over-current, over-voltage and plug over-temperature.

  • Ground-truth safety lives here — nothing upstream can close a relay without an intact pilot handshake.
  • Faults surface upward as state codes, so an operator three networks away sees GFCI, not a timeout.
Layer 2 · charger controller

ESP32 inside the charger

UART to the power board · Wi-Fi AP + STA · HTTP API · OCPP 1.6J client

Speaks a compact ASCII line protocol down to the power board, and offers a local HTTP API upward. It can talk OCPP straight to a cloud CSMS on its own — and it can charge with no network at all, in offline plug-and-charge mode.

  • Its own hotspot self-hides five minutes after first use, then un-hides automatically if Wi-Fi drops — so a technician can always get back in.
  • It can even reflash the power board's firmware from an image it carries itself.
Layer 3 · the gateway

The box that makes a site a fleet

Two hardware families, one identical behaviour contract

The gateway is the piece I care most about. It finds the chargers on the local network by scanning the subnet and fingerprinting each one, claims ownership, then polls them in a tight loop and republishes everything as one clean stream. Crucially, it keeps doing that whether or not the internet exists.

  • Two builds — a wired ESP32-S3 and a Raspberry Pi running Python asyncio under systemd — that are interchangeable from the cloud's point of view.
  • Offline it buffers to SD card (ESP32) or SQLite (Pi), and replays the backlog reliably on reconnect.
  • It is provisioned over Bluetooth from a phone — pick the site Wi-Fi, pick the chargers, and the gateway hops from charger to charger handing out credentials. No cables, no cloud.
Layer 4 · energy

Meter nodes & dynamic power sharing

Long-range radio meters · per-phase CT measurement · live load subtraction

A building's breaker is a hard ceiling, and EV chargers will happily blow through it. Panel meter nodes report the building's live draw — over long-range radio, so no new wiring — and the gateway continuously re-divides whatever headroom is left between the cars actually plugged in.

  • Every charger holds a 6 A floor; the surplus is water-filled to the cars that can use it, and re-divided the instant one finishes.
  • Options that matter in the field: equal vs. demand-led splitting, gentle ramping instead of jitter, reclaiming amps from a car that has tapered off, priority tiers, and a time-of-use cap for peak-rate windows.
  • If a meter goes quiet, the panel does not guess — it blocks new starts, and the operator can explicitly fall back to a static breaker-minus-buffer budget.
Layer 5 · transport & backend

Broker, server, database

Managed MQTT over TLS · Node.js on a cloud VM · Postgres as the record

One shared topic namespace that every gateway — regardless of hardware — speaks identically. A single always-on backend is the only thing holding broker credentials: it fans commands out, mirrors all traffic into the database, rotates security keys, and issues the browser's session tokens.

  • No client ever touches the broker directly. That one rule is what makes the whole thing auditable.
  • Retained status plus last-will means the fleet roster is correct even for a gateway that died thirty seconds ago.
Layer 6 · the operator

The console people actually use

Browser SPA · live WebSocket state · hand-written, no framework

A fleet list that drills into one gateway, every charger as a live card, and one-tap controls that are honest about what is happening — a spinner that lasts until the field device really answers, a retry when a packet gets dropped, and a specific reason when it fails.

  • A live MQTT wire log you can watch and download; a filterable browser over the whole event history with CSV export.
  • Fleet-wide firmware updates with per-device progress, and a raw command console covering the charger's full API surface.
  • Alongside it: a Windows operator kiosk that falls back MQTT → Bluetooth → direct hotspot, and a mobile app for technicians on site.
Layer 7 · getting paid

Offline sessions → real OCPP transactions

The flow that turns a survived outage into revenue

Surviving an outage is only half the job. The backend reads the replayed buffer, reconstructs each charging session as genuine OCPP 1.6J transactions backdated to when they actually happened, and streams them to the charge-point management system — with the meter samples and fault events in between.

  • Ingest is idempotent: a session already sent is never sent twice, so nobody gets billed twice.
  • Three targeting modes, because real sites differ: reuse each charger's own provisioned CSMS, treat the gateway as one charge point with connectors, or give each charger its own endpoint.
  • A dry-run test proves the link with a boot and heartbeat, so the provider sees the charger online before a real outage happens.
Section 02 · scope of the build

What that meant, discipline by discipline

Not a list of technologies. A list of problems that each needed a different kind of thinking.

Embedded C / C++

Two processors, one charger

A serial line protocol between the safety-critical power board and the network controller, firmware flashing across that same line, and a local API surface of roughly 45 commands that both a phone and a factory test rig drive.

Gateway firmware & services

The same contract, twice

Device discovery and ownership, a polling loop tuned per platform, durable offline buffering, Bluetooth provisioning and Bluetooth operation, and self-updating firmware that verifies before it commits and rolls back if it doesn't.

Energy & control

Allocation you can defend

Per-phase current measurement across six wiring topologies, CT calibration, rolling-peak headroom, and an allocator whose behaviour under scarcity is defined rather than emergent.

Cloud & data

One credentialed door

A single broker client, token-based sessions, full traffic mirroring into Postgres, rotating security keys pushed to the whole fleet on a schedule, and a firmware distribution path pinned to a known root of trust.

Front end

Live, without the flicker

Live state applied in place instead of re-rendering, so a table you are reading does not jump. Command state that reflects reality — including the unglamorous parts: dropped packets, reassembled multi-part replies, superseded intent.

Protocol integration

Speaking the industry's language

OCPP 1.6J both as the charger's own client and as something the backend synthesises on the charger's behalf after the fact — connector state machines, transaction lifecycle, meter values, firmware status.

Manufacturing

From bare board to shippable

A four-station production line: dual-processor flashing, identity and variant configuration, voltage calibration, and a final load test against an electronic load over MODBUS — every result logged and keyed to the board's serial.

Documentation

Explaining it to humans

Three interactive architecture walkthroughs, seven animated field procedures, and a full-screen site simulator — including a load-sharing sandbox that runs the production allocation logic in the browser so anyone can prod it.

Section 03 · decisions

The choices I'd defend in a review

Systems like this are judged on their failure modes, not their happy path.

Why can no client touch the broker?
Because credentials that live in a browser or a phone are credentials you have lost. One always-on backend holds them, which also means one place sees every publish, one place writes history, and one place to audit.
Why buffer on the device instead of retrying?
An outage lasting hours is normal at a parking structure. Retries drop data; a durable local buffer plus reliable replay on reconnect does not. The gateway treats the cloud as optional, never as required.
Why rotate a key the field can't reach?
The rotating key is the bridge between online and offline. The backend issues it while a gateway is online; the same key is what local Bluetooth and hotspot control validate later. So a gateway that drops offline is still operable — with the last key it confirmed, and nothing older.
Why is a missing meter a hard stop?
A load balancer that guesses when it loses its input is worse than one that refuses. If the panel meter goes quiet, new starts are blocked and the operator is told exactly why — with a deliberate, visible fallback to a static budget if they choose it.
Why backdate the OCPP transactions?
Because a session that happened at 2 a.m. during an outage is a 2 a.m. session. Ingesting it at the current timestamp would be convenient and wrong — wrong tariff window, wrong report, wrong invoice.
Why no front-end framework?
The console is a live instrument that runs for days on a wall display. Updating state in place — rather than re-rendering — keeps it flicker-free and predictable, with no build step between a fix and a deploy. A deliberate constraint, not an aesthetic one.
